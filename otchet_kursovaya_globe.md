# ВВЕДЕНИЕ

Современные веб-сервисы для планирования путешествий должны обеспечивать пользователю быстрый доступ к ключевым функциям без сложной предварительной настройки. На практике человеку важно не только найти направление поездки, но и удобно хранить информацию о маршруте, бюджете, списке вещей и погодных условиях.

Актуальность работы связана с тем, что многие существующие решения либо перегружены дополнительными функциями, либо требуют обязательной регистрации и длительного освоения интерфейса. Для учебного проекта особенно важно показать не только визуальную часть, но и архитектурный подход к построению интерфейса, использование модульной структуры, применение ООП и работу с внешними источниками данных.

Цель курсовой работы состоит в разработке клиентской части веб-приложения Globe для планирования путешествий. Приложение предназначено для хранения сведений о поездках, управления личным кабинетом пользователя, отображения погодных данных, ведения бюджета, чек-листа и заметок.

Для достижения цели необходимо решить следующие задачи:

1. Проанализировать предметную область и определить функциональные требования к продукту.
2. Обосновать выбор стека технологий для реализации клиентской части.
3. Спроектировать структуру интерфейса и состав экранов.
4. Реализовать страницы и модули приложения с использованием HTML, CSS и JavaScript.
5. Интегрировать внешний API для получения погодных данных.
6. Организовать хранение пользовательских данных на стороне клиента.
7. Проверить работу основных сценариев приложения.

Практическая значимость работы заключается в том, что полученное решение можно использовать как основу для учебного проекта, а также расширять за счет подключения полноценного бэкенда, авторизации, синхронизации данных и публикации поездок между пользователями.

# 2. АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И ФОРМИРОВАНИЕ ТРЕБОВАНИЙ

## 2.1 Анализ предметной области

Планирование путешествий включает несколько типичных этапов: выбор направления, определение дат, расчет бюджета, составление списка вещей, отслеживание погодных условий и сохранение заметок. Эти действия удобно объединить в одном интерфейсе, чтобы пользователь не переключался между несколькими приложениями.

Для туриста особенно важны три аспекта:

- удобство быстрого ввода информации;
- визуальная наглядность данных о поездке;
- доступ к актуальным погодным сведениям.

На основе этих потребностей в проекте реализованы три основных пользовательских сценария:

1. Переход на главную страницу и знакомство с сервисом.
2. Вход в личный кабинет и управление поездками.
3. Открытие отдельной поездки и работа с ее параметрами.

Приложение ориентировано на индивидуальное использование, поэтому вся логика хранения сведений реализована на стороне клиента. Такой подход подходит для учебной работы и позволяет не усложнять проект серверной частью, не связанной с ключевой задачей фронтенд-разработки.

## 2.2 Обзор и выбор технологий

Для реализации проекта выбран следующий стек технологий:

- HTML5 - для построения структуры страниц;
- CSS3 - для оформления, адаптивной верстки и реализации визуальных состояний;
- JavaScript (ES6+) - для логики интерфейса, обработки событий и взаимодействия с данными;
- Node.js и Express - для локального сервера и проксирования запросов к погодному API;
- Fetch API - для получения данных из внешнего источника;
- localStorage - для сохранения пользователей, поездок и пользовательских настроек;
- Git - для контроля версий.

Выбор нативного JavaScript вместо тяжелого фреймворка обусловлен тем, что проект состоит из относительно небольшого числа экранов и не требует сложной реактивной модели. При таком объеме логики использование чистого ES6+ делает код короче, прозрачнее и проще в сопровождении.

Express применяется для двух задач: раздачи статических файлов и обработки маршрута `/api/weather`. Это позволяет избежать CORS-проблем при обращении к стороннему погодному сервису и сохраняет простую структуру проекта.

## 2.3 Требования к продукту

Функциональные требования:

1. Главная страница должна знакомить пользователя с сервисом и содержать форму авторизации.
2. Пользователь должен иметь возможность зарегистрироваться и войти в систему.
3. После входа должен открываться дашборд со списком поездок.
4. Пользователь должен создавать новые поездки, удалять их и открывать подробную страницу.
5. На странице поездки должны отображаться погодные данные, бюджет, список вещей и заметки.
6. Данные пользователя должны сохраняться между сеансами работы браузера.
7. Интерфейс должен поддерживать светлую и темную тему.

Нефункциональные требования:

1. Приложение должно быть адаптивным и корректно отображаться на мобильных устройствах.
2. Интерфейс должен быть понятным без специальной подготовки.
3. Код должен быть структурирован по модульному принципу.
4. Пользовательский ввод должен экранироваться для снижения риска XSS.
5. Приложение должно корректно работать в современных браузерах.

# 3. ПРОЕКТИРОВАНИЕ ИНТЕРФЕЙСА И АРХИТЕКТУРЫ

## 3.1 Концепция продукта

Globe представляет собой клиентское веб-приложение для планирования путешествий. Продукт ориентирован на сценарий, когда пользователь хочет быстро создать поездку, сохранить основные параметры и вернуться к ним позднее.

Главный смысл интерфейса заключается в разделении работы на логичные экраны:

- главная страница - презентация сервиса и вход;
- дашборд - список поездок и управление ими;
- страница поездки - детальная работа с конкретным путешествием.

## 3.2 Структура проекта

Проект организован по модульному принципу. Исходный код находится в папке `src`, а страницы отображаются из каталога `frontend`.

Основные слои проекта:

- `src/pages` - классы страниц;
- `src/blocks` - переиспользуемые блоки интерфейса;
- `src/services` - работа с хранилищем и внешним API;
- `src/utils` - вспомогательные функции;
- `src/styles` - стили страниц и блоков.

Такое разделение делает проект удобным для расширения. Например, отдельный блок можно изменять без переписывания логики страницы, а сервисы можно заменить на полноценные HTTP-запросы к серверу.

## 3.3 Проектирование пользовательского интерфейса

При проектировании интерфейса использовались принципы минимализма и последовательности. Основной экран должен быстро объяснять назначение сервиса, а рабочие экраны должны быть сосредоточены на конкретных задачах пользователя.

Визуальная система построена на БЭМ-структуре классов. Это упрощает поддержку стилей и делает HTML-разметку более предсказуемой.

Особенности интерфейса:

- навигация реализована через логические блоки и кнопки;
- используются модальные окна для регистрации и создания поездок;
- темы переключаются отдельной кнопкой;
- информация на странице поездки разделена на независимые секции.

# 4. РЕАЛИЗАЦИЯ КЛИЕНТСКОЙ ЧАСТИ

## 4.1 Общая схема работы приложения

Точка входа находится в файле `src/index.js`. При загрузке страницы приложение определяет текущий экран и инициализирует соответствующий класс страницы. Такой подход позволяет использовать единый JavaScript-модуль для нескольких HTML-страниц.

В проекте реализована следующая логика:

1. Страница загружается в браузере.
2. Скрипт определяет тип страницы по `data-page` или URL.
3. Подключается менеджер темы.
4. Инициализируется нужная страница.
5. На странице навешиваются обработчики событий.

## 4.2 Главная страница

Главная страница выполняет презентационную и навигационную функцию. Она содержит описание сервиса, блок преимуществ, отзывы, контакты и форму входа.

За работу с этой страницей отвечает класс `MainPage`. Он проверяет наличие текущего пользователя и, если пользователь уже авторизован, перенаправляет его на дашборд. Если авторизация отсутствует, подключаются следующие блоки:

- навигация `Nav`;
- переключатель отзывов `FeedbackTabs`;
- модальное окно авторизации `AuthModal`.

Модальное окно авторизации позволяет зарегистрироваться и войти в систему. Информация о пользователях хранится в `localStorage`. Для учебного проекта такой подход удобен тем, что не требует отдельной серверной базы данных.

## 4.3 Панель пользователя

Страница дашборда предназначена для просмотра и управления поездками. Она реализована в классе `DashboardPage`.

На этой странице пользователь может:

- увидеть список всех своих поездок;
- создать новую поездку;
- удалить существующую поездку;
- открыть подробный экран конкретной поездки;
- выйти из учетной записи.

При отсутствии поездок отображается пустое состояние, которое мотивирует пользователя создать первую запись. Для добавления поездки используется модальное окно с формой. При создании проверяется корректность дат: дата окончания не может быть раньше даты начала.

Карточка поездки содержит название, направление, даты и бюджет. Для защиты интерфейса от небезопасного ввода применяется экранирование текста.

## 4.4 Страница поездки

Страница поездки является центральным рабочим экраном приложения. Она реализована в классе `TripPage` и включает несколько независимых блоков.

### Погодный блок

Для получения погодных данных используется отдельный серверный маршрут `/api/weather`. Локальный сервер отправляет запрос к Open-Meteo API, получает координаты города и текущую погоду, а затем возвращает необходимые данные клиенту.

Пользователь видит:

- температуру;
- описание погоды;
- скорость ветра;
- название города и страны.

### Бюджет

Если у поездки указан бюджет, на странице отображается блок расходов. Пользователь может добавлять затраты, видеть потраченную сумму, остаток и визуальный индикатор заполнения бюджета.

### Список вещей

Список вещей реализован как интерактивный чек-лист. Пользователь может добавлять пункты, отмечать выполненные элементы и удалять ненужные записи. Для удобства отображается прогресс по количеству собранных вещей.

### Заметки

Секция заметок позволяет сохранять дополнительную информацию о поездке. Сохранение выполняется с задержкой после ввода, чтобы не перегружать хранилище частыми записями.

## 4.5 Интеграция с внешним API

В проекте используется внешний погодный сервис Open-Meteo. Для скрытия внешнего запроса и обхода ограничений CORS создан промежуточный маршрут на сервере. Это упрощает клиентский код и делает архитектуру более предсказуемой.

Сервис погоды инкапсулирован в классе `WeatherService`. Он содержит два ключевых метода:

- `getCurrentWeather(city)` - получает текущую погоду по названию города;
- `getDescription(code)` - переводит код погоды в человекочитаемое описание.

Такой подход удобен тем, что логика получения данных отделена от логики отображения.

## 4.6 Хранение данных на стороне клиента

Для хранения пользователей, текущей учетной записи и списка поездок используется `localStorage`. Управление данными вынесено в `StorageService`.

В хранилище сохраняются:

- список зарегистрированных пользователей;
- текущий авторизованный пользователь;
- поездки конкретного пользователя.

Достоинство такого решения - простота и отсутствие внешних зависимостей. Недостаток - отсутствие синхронизации между устройствами и невозможность полноценного восстановления данных без серверной базы.

# ПРИЛОЖЕНИЕ В

## Краткое описание серверной части

Файл `server.js` выполняет две основные задачи:

1. раздает статические файлы фронтенда;
2. предоставляет маршрут `/api/weather` для получения погодных данных.

Маршрут работает по следующей схеме:

- принимает название города;
- обращается к геокодеру Open-Meteo;
- получает координаты города;
- запрашивает текущую погоду;
- возвращает клиенту упрощенный JSON-ответ.

Это позволяет клиентской части работать независимо от прямого обращения к внешнему API и упрощает обработку ошибки сети.
